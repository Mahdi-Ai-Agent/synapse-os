# Decisions (ADR-lite)

One entry per architectural choice: date, decision, why, alternatives considered. Newest last. Change a decision by adding a new entry that supersedes the old one.

## 2026-10-31 — Project name: Synapse
Chosen by the user over Mind, Neura, Mindgraph. Package scope `@synapse/*`.

## 2026-10-31 — Markdown + frontmatter is the source of truth; the app keeps a derived index
Why: the brain is an agent that edits files with native tools; files are portable, diffable, git-versionable and Obsidian-compatible. Alternatives: SQLite as primary (faster queries at scale, but the AI needs an API layer and export is a second format). Revisit if vaults exceed ~10k nodes.

## 2026-10-31 — Vault lives outside the repo (`~/Synapse/vault` by default)
Why: Claude Code loads `CLAUDE.md` from every parent directory, so a vault inside the repo would pull developer instructions into the brain's context. Also: user data must never be committed with code.

## 2026-10-31 — Dual instruction files: `AGENTS.md` canonical, `CLAUDE.md` imports it
Why: Codex and other agents read `AGENTS.md`; Claude Code reads `CLAUDE.md` first and includes `AGENTS.md` through `@AGENTS.md` (verified in Claude Code docs, no double-loading). Same pattern in the repo and in the vault.

## 2026-10-31 — Brain v1 spawns the user's installed, unmodified `claude` CLI in headless mode
Why: Anthropic's legal page allows an end user to sign in to the unmodified binary with their own subscription and forbids apps from collecting or proxying credentials. Synapse never touches credentials; login happens in Claude Code. Alternatives: Claude Agent SDK (API-key use for products), direct Anthropic API (API key; Phase 4). Flag: public distribution must follow the "preinstalled Claude Code" conditions.

## 2026-10-31 — Graph rendering with `react-force-graph-2d` / `-3d` + `graphology`
Why: one API for 2D canvas and 3D WebGL, custom canvas painting for glow/RTL labels, link particles, d3-force-3d physics, MIT. Alternatives: sigma.js (2D WebGL, more custom shader work), cosmograph (GPU, limited customization), reagraph (React 3D only).

## 2026-10-31 — No native dependencies in v1 (no SQLite); in-memory index + JSON cache
Why: personal vaults are small (hundreds to a few thousand nodes); rebuilding the index from files takes milliseconds; avoids native builds in Tauri/mobile later. Add `sqlite-vec`/embeddings only with an API-key engine (Phase 3+).

## 2026-10-31 — Web stack: Vite + React 19 + Tailwind 4 + Zustand; fa default, RTL, en toggle
Why: fastest path to a polished local UI that later wraps into Tauri unchanged. i18n via plain dictionaries (no runtime library) to keep the bundle small.

## 2026-10-31 — Server: Fastify + WebSocket; chokidar watcher; vault history through plain `git`
Why: every brain run becomes a commit → free undo and history; manual edits are snapshotted before a run so diffs attribute changes correctly.

## 2026-10-31 — Index tiers: `index/INDEX.md` router + `index/by-type/*.md`, generated by the app
Why: the context-economy law applied to data — the brain reads one small router, then only the slice it needs. The brain never edits `index/` (hook-enforced); the app regenerates it on every change.

## 2026-10-31 — Wikilinks by title (Obsidian-compatible) with a ULID `id` as the stable key
Why: readable links for humans and the brain; renames rewrite links by id. Unresolved links become ghost nodes in the graph.

## 2026-10-31 — Pin TypeScript 5.9.x; scripts in TypeScript via `tsx`
Why: TypeScript 7 (native compiler) is too new for the surrounding tooling; one language for app, scripts, eval harness (agent-creator used Python, which is fine there but adds a second toolchain here).

## 2026-10-31 — Frontmatter parsed with js-yaml's CORE schema (no gray-matter)
Why: the default YAML schema turns `2026-11-05` into a JS `Date`, which breaks round-tripping and comparisons; CORE keeps dates as strings and lets the serializer write them unquoted. One small splitter + js-yaml replaces gray-matter.

## 2026-10-31 — Missing `id`/`created`/`updated` are filled by the app, not demanded from the brain
Why: asking an LLM to generate ULIDs is error-prone; `loadVault` heals files that lack them and rewrites only those files. The brain's rules say "leave `id` and `created` out when creating a node".

## 2026-10-31 — Login state comes from `claude auth status`; the server spawns the CLI with a sanitized env
Why: `auth status` prints JSON with `loggedIn` for free; a paid probe call was the alternative. Host-session env vars (`CLAUDECODE`, `CLAUDE_CODE_*`, `CLAUDE_AGENT_SDK_*`) made a 1 s headless start take 12 s and leaked host state, so they are dropped.

## 2026-10-31 — Graph fit ignores orphans; nodes keep their objects across filter changes
Why: `zoomToFit` over all nodes makes the graph tiny when a few orphans drift away under the repel force. Node objects are cached per id so the simulation keeps positions when filters, focus or data change.

## 2026-10-31 — Review skills write only to the journal; `daily`/`weekly` are brain modes
Why: a review must be cheap, repeatable and reversible — one appended journal entry per run (`brain(daily|weekly)` commit), while the weekly review lists *proposed* edits for the user to approve instead of mass-editing nodes. The server prefixes `/daily` or `/weekly` like it does `/capture`, so the Today buttons, the runtime context and the commit prefix all name the mode. Alternative: sending `/weekly` through `chat` (no mode label, `brain(chat)` commits).

## 2026-10-31 — The vault's agent layer is app-owned and re-synced on every server start
Why: skills and rules ship with the app, and an existing vault would otherwise keep the agent layer it was created with (the `daily`/`weekly` skills never reached `~/Synapse/vault`). `syncAgentLayer` copies only `AGENTS.md`, `CLAUDE.md`, `.claude/**`, `.gitignore`; `memory/` and `nodes/` stay the user's. Alternative: an explicit "upgrade vault" action (easy to forget; the brain would silently run stale instructions).

## 2026-10-31 — Related nodes are lexical ("more like this" over the MiniSearch index), dismissals live in `.synapse/`
Why: no embeddings without an API-key engine (Phase 4), and BM25 over title/tags/summary/body with the node's own top terms as the query is good enough on personal-vault sizes and explains itself (shared terms are shown). Already-linked nodes, inbox and journal entries are excluded. Dismissed pairs are app-private (`suggestions.json`), never written into node files, so the vault stays clean for other tools.

## 2026-10-31 — WYSIWYG body editing: TipTap 3 + official `@tiptap/markdown`, a `wikilink` atom node, byte-stable unchanged bodies
Why: TipTap is headless, React-friendly and its official Markdown extension (marked-based) accepts per-node tokenizers, so `[[Title]]`, `[[Title#h]]`, `[[Title|alias]]` parse into an atom node and serialize back verbatim. The stock serializer escapes `_ [ ] & < >`, which would rewrite plain vault prose (`belongs_to`), so a subclass replaces the escaping with a minimal, flanking-aware one. Exact bytes cannot survive any re-serialization, so the editor compares the document with the one it loaded and hands back the original string when nothing changed; real edits are written in canonical Markdown. Alternatives: `tiptap-markdown` (community, TipTap 2 era), `prosemirror-markdown` with a hand-written schema mapping, CodeMirror (not WYSIWYG).

## 2026-10-31 — Rename = textual link rewrite in backlinking files + alias; the file name is kept
Why: the ULID is the stable key and the slug is only a file name, so renaming the file would break nothing in Synapse but would churn git history and external references for no gain. Links are rewritten as raw text (`rewriteWikilinks`, code spans skipped) in exactly the files that resolve to the node, so untouched frontmatter in those files is not re-serialized and their `updated` stays. The old title becomes an alias so links written later from memory still resolve. The rename is its own commit after a snapshot of pending edits. Alternative: re-serialize every backlinking node through `serializeNode` (normalizes YAML the brain wrote).

## 2026-10-31 — Frontmatter that is not valid YAML is recovered line by line and normalized, never degraded
Why: the brain wrote `summary: مرور روزانه: ۲ عقب‌افتاده` (an unquoted `: `), js-yaml threw, the parser fell back to derived defaults and the self-heal rewrote the file with them — the node lost its id, title, date and summary (data loss, commit `acf2ea1` in the vault). Now `parseLenientFrontmatter` recovers `key: value`, block lists and inline lists; a recovered node is written back as valid YAML (quoted); a file nothing can parse is reported as an error and left byte-for-byte alone. The vault's `node-format` rule tells the brain to quote values containing `: `.

## 2026-10-31 — Graph gravity force toward the origin
Why: nodes without links drift away under the repel force, and any fit over all nodes shrinks the connected graph to a dot. A small inline `gravity` force (strength = the "center" slider) keeps orphans near the cluster; no new dependency.

## 2026-10-31 — API-key engines run an in-app tool loop over the providers' APIs, not the Claude Agent SDK
Why: one loop (`packages/brain/src/tool-loop.ts`) serves Anthropic, OpenAI and OpenRouter; its five file tools are confined by construction (reads never touch `.synapse/` or `.git/`, writes only `nodes/` and `memory/` — the same boundary the vault hook enforces for Claude Code), and no third CLI spawn path is needed. The Anthropic provider uses the official `@anthropic-ai/sdk` (streaming, typed errors, prompt caching); OpenAI and OpenRouter share one `fetch`-based Chat Completions provider. Server-side refusal fallbacks (`fallbacks: "default"`) are deliberately not enabled — a vault brain never hits those categories and there is no key to verify the beta against yet. Alternatives: Claude Agent SDK (Claude-only, a Claude Code harness billed to an API key), the `openai` npm package (a second SDK for the same wire format).

## 2026-10-31 — Engines without native `AGENTS.md`/skills/rules support get the agent layer in the prompt
Why: Codex reads `AGENTS.md` from cwd but has no system-prompt flag, does not expand `/capture`-style skills and never loads path-scoped `.claude/rules/*.md`; the API engines have none of it. So `loadAgentLayer` (`packages/brain/src/agent-layer.ts`) reads the vault's `AGENTS.md`, `memory/profile.md`, `memory/lessons.md`, rules (with their `paths:`) and skills once per run: Codex gets `<runtime_context>`, a `<folder_rules>` index and the expanded skill in its prompt; the API engines get a cached stable system block plus the runtime context, and each matching rule's full text is appended to the first tool result that touches its folder — mirroring Claude Code's on-demand loading without spending the tokens up front. The vault template itself is unchanged, so `pnpm vault:context` and the Claude Code path are unaffected.

## 2026-10-31 — API keys: Settings beats the environment, keys are served masked, the file is owner-only
Why: a key pasted in Settings must take effect without restarting the server, so `.synapse/settings.json` `apiKeys` is consulted before `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `OPENROUTER_API_KEY` (the server loads the repo `.env` at start). The file lives in `.synapse/`, which the vault's `.gitignore` excludes, and is written with mode 600; `GET /api/settings` and `/api/vault` only ever return `sk-ant-…cdef`-style previews. Probes stay free: a missing key is reported with the exact fix, a present key is checked with the provider's models/auth endpoint (401 → "rejected"), a network failure leaves it "not verified" but usable.

## 2026-10-31 — Per-engine model/effort defaults; `model`/`effort` mirror the selected engine
Why: `sonnet`/`medium` meant nothing to Codex or OpenRouter, so switching engines carried a wrong model along. Settings now keep `engines[id] = {model, effort}`; `PUT /api/settings {engine}` mirrors that engine's defaults into the legacy top-level `model`/`effort`, and the composer resets its pickers when the selected engine changes. A thread remembers the engine of its session: a run on a different engine starts a new engine session in the same thread.

## 2026-10-31 — Provider assistant turns are replayed verbatim (thinking blocks, `reasoning_details`)
Why: Claude 5.x binds thinking blocks to the conversation and expects assistant turns echoed unchanged in tool loops, and Anthropic models behind OpenRouter need their `reasoning_details` back; the neutral transcript therefore carries the provider's raw assistant payload next to the text and tool calls. Transcripts live under `.synapse/engine-sessions/<engine>/`; threads longer than 120 messages start a fresh context instead of editing history.

## 2026-10-31 — LAN access: loopback is trusted, every other address presents a pairing token
Why: Synapse is single-user and local; the desktop flow must stay zero-friction while a phone on the same Wi‑Fi must not be able to read or edit the vault (or spend the user's AI budget) without proof it belongs to the user. The proof is one secret created by the server (`crypto.randomBytes(32)`, base64url, `.synapse/pairing.json` mode 600) handed over out of band by a QR code (`/#pair=<token>`: a fragment never hits the server or its logs) and presented as `Authorization: Bearer` on the API and `?token=` on the WebSocket upgrade (browsers cannot set upgrade headers). Comparison is constant-time over SHA-256 digests; the token is never logged (URL redaction in the request serializer) and only loopback callers may read or rotate it or switch `server.lanAccess`; `X-Forwarded-For` is never trusted; the static shell is public code. LAN binding is opt-in (`server.lanAccess` or `SYNAPSE_HOST`) and re-bound at runtime so the QR appears without a restart. Alternatives: no auth on the LAN (any device on the Wi‑Fi could edit the vault); a cookie session after a one-time code (needs CSRF defences and does not survive iOS's separate home-screen storage, which the token does through the manifest `start_url`); per-device tokens with a device list (more state than one user needs; revisit if more than one phone pairs); HTTPS client certificates (deferred, below). Model: `ARCHITECTURE.md` "Access control".

## 2026-10-31 — One origin in production, no service worker, plain HTTP on the LAN
Why: the phone must open one URL, so the Fastify server serves `apps/web/dist` (`@fastify/static`, SPA fallback) next to `/api` and `/ws`; `pnpm dev` keeps the Vite proxy. Secure-context rules decide the rest: service workers register only in secure contexts, and only `localhost`/`127.0.0.1`/`*.localhost` count as potentially trustworthy over plain HTTP — `http://192.168.x.x` does not — so a service worker would never run for the phone and offline caching is not a requirement anyway (the brain needs the desktop). Chrome dropped the service-worker requirement for installing from its menu (108 on Android, 112 on desktop) but still requires a secure context, so on Android "Add to Home screen" over LAN HTTP yields a shortcut that opens in the browser; iOS Safari honours the manifest (`display: standalone`, icons, `start_url`) on HTTP and opens a standalone app. Because that app has its own storage, a paired client requests the manifest with `?token=` and the server writes the token into `start_url`. Deliberately deferred: HTTPS on the LAN with a self-signed or mkcert certificate (needs the certificate installed on every phone; a natural Tauri 5b task where the desktop app can manage it), tunnels such as Tailscale (outside the app), a service worker for offline reading. Sources: W3C Secure Contexts, MDN "Secure contexts", developer.chrome.com "Revisiting Chrome's installability criteria".

## 2026-10-31 — The phone is a layout mode of the same web app (breakpoint 768px), not a second app
Why: one bundle, one state, one i18n; the desktop DOM is untouched (the layout branches once in `App.tsx` on a `matchMedia` hook, and components take `mobile`/`sheet` props instead of responsive class soup). Composer-first: a bottom tab bar (Today · Inbox · Capture · Graph · More) replaces the rail, the composer fills the Capture tab, the node panel becomes a full-screen sheet, the graph gets touch pan/pinch (`touch-action: none`) and larger hit targets on coarse pointers, and the shell height follows the visual viewport so the composer stays above the on-screen keyboard. Alternatives: a separate mobile bundle (duplicated views), responsive Tailwind variants throughout (risks desktop regressions), a native companion (Phase 5c). Spec: `UI-DESIGN.md` "Phone layout".
## 2026-10-31 — Inbox items are consumed by the app, not deleted by the brain
Why: `claude-cli` runs with `--tools Read,Edit,Write,Glob,Grep,Skill` (no Bash), so the brain filed inbox items but could not delete them — two real runs ended with "I don't have a delete tool". Now `/capture` marks the item `status: filed` (an Edit every engine has) and the server deletes filed inbox files, plus the file a run was started for from the Inbox view once the run changed anything, before the `brain(capture)` commit — so the deletion is part of the undoable commit and the original stays in git history. A run that targeted an inbox item but changed nothing ends with "nothing was filed" and the item stays. Alternatives: a `Bash(rm …)` allow rule (opens a shell to the brain for one verb), deleting on every capture regardless of outcome (would drop unfiled items).

## 2026-10-31 — "File all" is a client-driven batch: one item per run, one thread, started one after another
Why: one prompt listing every item gave no per-item feedback and let the brain skip items silently; enqueueing all items at once would push every user message into the thread before any reply. The Inbox view starts the next run when `brain.done` arrives for the previous one, in the thread the first run created (`--resume` keeps the brain's context), with a "n of total" label; Stop cancels the running item and releases the rest. The server still serializes everything, and `brain.queue` / the run response's `position` make real waiting visible. Alternative: a server-side batch endpoint (more state to persist and resume for little gain on personal inbox sizes).

## 2026-10-31 — The graph gets its own three.js renderer (WebGL) instead of react-force-graph
Why: the user asked for a graph that feels alive and "real" — regions per category, colour families, glow, motion, zoom effects — and found the canvas version flat and cluttered. A purpose-built renderer gives what the wrappers cannot do cleanly together: instanced billboard nodes drawn by a signed-distance shader (crisp shapes per type, one draw call), bloom post-processing, nebula shaders per category, a starfield with real parallax from a perspective camera, signal pulses along links, smooth critically-damped pan/zoom/fly-to, screen-space picking with generous hit areas, and DOM labels placed without overlaps (crisp Persian shaping and bidi for free). Layout stays d3 (`d3-force-3d`, so the flat and 3D modes share one simulation) with custom category forces. Alternatives: react-force-graph-2d with sprite glow (no real bloom or depth, labels still canvas-drawn); 3d-force-graph with `UnrealBloomPass` (one mesh per node, link gradients and drift fight its update loop); cosmos.gl (GPU layout with clusters, but fixed point shaders and no per-node styling); sigma.js v3 (good clustering, custom WebGL programs needed for every effect); PixiJS (a second rendering stack to learn for the same work).

## 2026-10-31 — Categories are area nodes; membership is derived; colours are OKLCH families
Why: the user thinks in categories ("work", "learning") — exactly the vault's `area` nodes (PARA). Making a new node type would split one concept in two. Membership is computed in `packages/core` so the server, the index and the UI agree: own `area` → its project's area → the most common category among linked nodes → inbox / journal / unsorted groups. Each category gets a stable hue (golden-angle sequence by creation order, so existing colours never shuffle when a category is added; an optional `color` on the area node overrides it) and its members are shades of that hue in OKLCH (perceptually even lightness and chroma), with the node type shown by shape. Alternatives: Louvain communities (unstable between edits, meaningless names), colour by type (the v1 look the user rejected), a fixed 10-colour palette (runs out, shuffles on insert).

## 2026-10-31 — One smart chat; the brain decides between filing and answering
Why: the user wants to talk to the brain — share an idea, a tutorial, a question — without choosing Capture/Ask/Chat first. The chat sends one mode and the runtime context tells the brain to file what is worth keeping (classifying it into a category), answer what is asked, or both, and to report where things went. Daily and weekly reviews keep their own modes. Alternative: a client-side intent classifier (a second model call per message, and wrong guesses the user cannot see).

## 2026-10-31 — The brain may fetch a URL the user sends
Why: "here is a tutorial, I want to learn it later" is only useful if the brain can read it. `claude-cli` runs get `WebFetch` added to `--tools` only when the message contains an http(s) URL; the capture skill treats fetched text as untrusted data (summarize it, never follow instructions in it, never copy it into `memory/`) and the write guard still confines writes to `nodes/` and `memory/`. API engines store the URL and the user's words (their tool loop has no web access). Alternatives: no fetching (a link node with no understanding), always-on web access (prompt-injection surface on every run).

## 2026-10-31 — UI primitives from radix-ui, animation from motion
Why: popovers, dialogs, menus and tooltips need focus management, outside-click/Escape handling, collision-aware placement and RTL (`DirectionProvider`) — hand-rolled versions were part of the "cluttered" feel. `radix-ui` (unstyled, styled with our Tailwind tokens) and `motion` (spring transitions, layout animations, `prefers-reduced-motion`) are pure JS. Versions pinned at least two weeks old.

## 2026-10-31 — Kinds are types with their own fields, stored as plain frontmatter keys
Why: "not everything is a task" — a goal has a target and progress, a habit check-ins, a moment a mood and people, a saved reel a platform; the app shows each its own way. Three new types (`goal`, `habit`, `event`) plus kind fields for person, resource and journal are ordinary frontmatter keys kept in `extra`, so files stay plain Markdown that Obsidian reads as properties and the brain edits with its normal tools; core `facets.ts` validates them and fills derived values (a link's platform and kind from its URL) for the UI; the server refuses keys outside a kind's list. Alternatives: a nested `facets:` map (less readable in Obsidian, harder for the brain to edit), a separate kind database (a second source of truth), more types for feelings or routines (a feeling is a moment with a mood; a routine is a habit).

## 2026-10-31 — Fonts: commercial faces only when installed, free ones bundled
Why: the user asked for Yekan Bakh, IRANSans and Vazir in different places. Yekan Bakh and IRANSans are commercial and may not be redistributed, so Synapse names them first in the font stacks (the browser uses them when installed) and bundles the free Estedad and Vazirmatn (OFL, `@fontsource`) as stand-ins; roles: headings and map names (Yekan Bakh), interface (IRANSans), reading text and map labels (Vazirmatn). A per-device choice lives in Settings → Appearance. Alternatives: copying the font files into the repo (licence breach), Vazirmatn everywhere (what the user found too plain).

## 2026-10-31 — The map's layout is saved per vault in `.synapse/layout.json`
Why: a region the user dragged, a node they pinned and where everything settled must survive a reload and look the same on the phone. The server stores anchors, pins and positions (validated, rounded, atomic writes) behind `GET/PUT/DELETE /api/layout`; the web app restores it before the first layout and saves it debounced after drags and settles, flat view only. Alternatives: `localStorage` (per browser, lost on another device), frontmatter coordinates (layout noise in the user's files and git history).

## 2026-10-31 — Link previews are fetched by the server, guarded against private addresses
Why: saved reels, videos and courses need a thumbnail and a title, and the browser cannot read other sites' Open Graph tags (CORS). `GET /api/preview` fetches the page (YouTube through oEmbed), refuses any host that resolves to loopback, private, link-local or CGNAT ranges (checked again after each redirect) so a link cannot make the server probe the LAN, caps time and size, and caches results in `.synapse/previews.json`. Alternatives: a third-party unfurl service (sends the user's links to someone else), no previews (the "link" kind would look like any note).

## 2026-10-31 — A chat-first shell: start-side sidebar, a chat page, the map as one page among others
Supersedes the Phase 6 shell (full-bleed graph with an end-side dock). Why: the user found the dock and its menus complicated, wanted a minimal ChatGPT/Claude-like chat page, and in Persian expected the chat side on the right. The sidebar sits on the start edge (right in Persian) with New chat, the pages and recent chats; the chat page is the home; item details open beside a page on the end side, and on the map on the start side under the search box (like a map app's place panel); the map stays mounted behind the pages so its camera and layout survive navigation. The Projects, People and Journal pages give way to the categories page's kind filters. Alternatives: keeping the dock on the start side (still two competing panels over the map), a chat-only app (loses the map the user values).

## 2026-10-31 — Map labels follow the zoom level like a map's names
Why: overlapping small labels were the user's main complaint. What is shown depends on the on-screen gap between neighbouring nodes (pixels per world unit × the layout's median nearest-neighbour distance): region names only from afar, then centres and big items, then everything — always placed without overlaps, keyed per node and faded. A click on a category flies into its region and opens its card. Alternatives: fixed distance thresholds (break with vault size), shrinking fonts (unreadable), canvas-drawn labels (no proper Persian shaping).

## 2026-10-31 — Finished stays, archived leaves: two closings with a `completed` stamp
Why: the user asked what "done" should mean on the map and to the brain. `done`/`achieved` is history — the item stays (hollow and faded on the map, folded under "Done" in its category, "Finished this week" on Today) and carries `completed`, which core keeps in step with `status` (`withCompleted`: set on the change, healed on load, cleared on reopening) so the brain, Obsidian and the app agree without a second write path; `archived`/`dropped` is out of sight — off the map unless asked for, last in the index. Alternatives: deleting finished items (loses the record the user wanted), one "closed" bucket (the map would hide what should stay), a server-only stamp (files edited elsewhere would drift).

## 2026-10-31 — One glyph per kind, drawn by the UI from the map's silhouettes
Why: the map already drew a shape per kind, but chips and cards used unrelated lucide icons, so the user saw no shared language. `TypeIcon` now draws the same silhouettes as the shader (`UI-DESIGN` "Shapes"); progress is drawn into the shape (a goal's ring closes, a project's hexagon fills) so a glance at the map carries the same facts as the card. Alternative: a legend only (teaches the mapping but does not make it visible everywhere).

## 2026-10-31 — Stepping back on the map returns the camera, unless the user moved it
Why: the user expects a click on empty map to undo the last step (item → category → nothing) and the zoom with it, like leaving a place on a map. `GraphView` remembers the camera's goal before every way in (`engine.cameraPose`, once per level) and every way out goes through `back()`; `engine.movedSince` (a counter of the user's own pans and zooms) decides whether the flight back would fight them. Alternatives: a full camera history (surprising after many moves), always flying back (fights a user who just zoomed where they wanted).

## 2026-10-31 — The chat opens fresh; past chats live in a column inside the chat page
Why: landing in the last chat and listing chats under the pages menu mixed navigation with history. The page starts a new chat every time it opens (a reply still streaming is the one exception) and the past chats fold out beside it, grouped by day, as in the chat apps the user named. Alternative: keeping the list in the sidebar (what Phase 7 did; rejected by the user).

## 2026-10-31 — Block direction by dominant script, not first strong letter
Why: `unicode-bidi: plaintext` laid out Persian paragraphs that open with a Latin label ("Outcome:") left-to-right, which read as broken RTL. Rendered Markdown and the editor now set each block's direction from the script most of its letters are in (`dominantDir`), and the brain's rules put lead-ins in the node's language. Alternative: fixing only the data (an English word at the start of any Persian line would break it again).

## 2026-10-31 — The brain asks before filing when the answer changes the filing
Why: the user wants a conversation, not a guess: which category, which kind, which facts a node needs. The rule (vault AGENTS.md step 4) names the cases — two categories fit or none, the kind is unclear, a fact the kind needs is missing — and bounds the cost: one message, the best guess, at most two questions, nothing filed until the answer, which lands in the same thread because the engine session resumes. A clear message still files at once. Alternatives: always file then ask (what Phase 7 did; empty nodes and corrections), a form in the UI (the user wants to talk).

## 2026-10-31 — Links are built from a category's sub-index, on a budget
Why: linking must read the least context. `index/by-area/<area>.md` lists one category's items on one line each — with people, project and tags, so a line alone says what a node touches — and the brain picks at most five candidates from it and opens only those. INDEX.md points to the files; they follow the graph's category assignment (inferred memberships included). Alternatives: grepping `nodes/` (slow, unbounded), embeddings (need an API key engine), reading every by-type file (most lines irrelevant).

## 2026-10-31 — Consult mode is a read-only skill, not a different brain

A run that sends nothing for 15 minutes is aborted with that reason, so a hung engine never holds the single-flight queue. The spawned `claude` also runs with the headless defaults (`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, no auto-update, telemetry or error reports), and the user's own `CLAUDE_CODE_*` settings are no longer dropped with the host-session variables.
Alternatives: keep Codex's `error` lines fatal and retry the run (would double the cost of a flaky network and still show an error); a shorter stall limit (a long reasoning phase without partial messages could trip it; 15 minutes is well past any retry schedule); a visible "diagnostics" page per run (the log line and the Diagnostics card are enough to find the slow part).

## 2026-11-02 — Export and import: one zip of the vault's own files without secrets; an import replaces everything
Why: the owner asked for a way to take all their data out of the deployment and bring it into the copy on their Mac (and back).
